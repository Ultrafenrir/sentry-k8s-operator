T04 — DSN AND OUTPUT SECRET
Updated: 2026-10-31
Status: Complete for source/mock/Kubernetes scope with live managed client-key configuration evidence

The operator lists project client keys, selects exactly one usable active key according to
policy, and publishes only its public DSN. Secret key material and private DSN components are
never written to CR status, Events, metrics, or logs.

Managed projects may publish their active default key after safe-create capabilities are
proven. Existing projects require explicit `consumeDSN` authorization. Observation alone
never grants DSN access.

The output Secret is namespaced with the `SentryProject`, owner-referenced to it, and uses
key `SENTRY_DSN`. The controller compares a content hash, repairs drift, and avoids writes
when the desired Secret is already present. Conflicting pre-existing ownership fails closed.

Changing the output Secret name uses a cutover state: publish and verify the new Secret,
retain the old usable Secret, require explicit confirmation, then remove the old output.
Temporary Sentry or Kubernetes failures preserve the last verified Secret.

Managed projects may declare bounded client keys under `spec.clientKeys`. The controller
creates server-generated keys, manages activation and portable rate limits, pins exact
external identities in protected state, and performs rotation through an increasing
`rotationRevision`. A replacement public DSN is published and verified before guarded
deletion of the prior exact key. The API, status, Events, metrics, logs, and operation
journals never contain the secret key or a private DSN. An absent `clientKeys` field leaves
keys unmanaged; an explicit empty map deletes only protected operator-owned keys.

Create and replacement operations use a durable hexadecimal intent journal. Recovery may
accept an exact ownership label only after a submitted journal record exists; a same-name
key without that evidence is never adopted. Protected state records only identities,
ownership labels, revisions, normalized rate limits, and hashes.

`make verify-t04` covers authorization, key selection, managed creation, redaction, drift,
rotation, guarded deletion, cutover, and failure behavior. `make verify-t04-kind` proves
that a workload requiring the Secret stays blocked until publication and starts afterward.
Clean configuration-only runs on both supported self-hosted versions prove managed
create/update/rotate/delete and public-DSN cutover through both the direct API gate and the
full controller. They do not prove event ingestion or notification delivery.
