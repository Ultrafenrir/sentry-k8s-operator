T04 — DSN AND OUTPUT SECRET
Updated: 2026-10-31
Status: Complete for source/mock/Kubernetes scope with live key/DSN configuration evidence

The operator lists project client keys, selects exactly one usable active key according to
policy, and publishes only its public DSN. Secret key material and private DSN components are
never written to CR status, Events, metrics, or logs.

Managed projects may publish their active default key after safe-create capabilities are
proven. Existing projects require explicit `consumeDSN` authorization. Observation alone
never grants DSN access.

The output Secret is namespaced with the `SentryProject`, owner-referenced to it, and uses
key `SENTRY_DSN`. The controller compares a content hash, repairs drift, and avoids writes
when the desired Secret is already present. Conflicting pre-existing ownership fails closed.

Changing the output Secret name uses a cutover state: publish and verify the new Secret,
retain the old usable Secret, require explicit confirmation, then remove the old output.
Temporary Sentry or Kubernetes failures preserve the last verified Secret.

`make verify-t04` covers authorization, key selection, redaction, drift, rotation, cutover,
and failure behavior. `make verify-t04-kind` proves that a workload requiring the Secret
stays blocked until publication and starts afterward.
