T06 — DESTINATIONS AND REGISTRATION
Updated: 2026-10-31
Status: Core policy, resolution, pinning, revoke state, and Telegram registration are
implemented. Real provider acceptance is deferred.

Implemented boundary

- readable Slack workspace/channel, PagerDuty account/service, and Telegram target
  selectors in the CRD;
- connection access policy that bounds each selector;
- exact resolution, duplicate rejection, protected identity pinning, rename/replacement
  detection, and explicit rebind;
- dependency-aware cleanup so a destination pin is retained until owned alerts release it;
- Telegram registration challenge issuance, expiry, one-time consumption, policy fencing,
  protected route publication, revoke, and restore state;
- separate public receiver and internal mTLS writer with no Kubernetes token on the public
  side;
- least-privilege RBAC, NetworkPolicy, certificate reload, and redacted status/metrics.

PagerDuty and Slack

PagerDuty public organization integration data provides account identity and a service table.
The production catalog resolves and pins those values but never decodes or exposes the
integration routing key.

No stable public Slack channel enumeration route has been proven across both supported
Sentry versions. Without an injected, version-compatible catalog the runtime returns
`DestinationUnsupported`; mock orchestration does not promote that capability.

Authoritative cleanup

Removing a local destination key does not delete a provider-owned Slack channel or
PagerDuty service. The protected binding enters cleanup-pending state until every owned
Sentry alert action is updated or deleted. Sentry errors preserve the binding and alert
identity for retry. Telegram follows the same dependency gate, then revokes the exact local
route with an audit record.

Telegram registration security

Challenges use 256 bits of randomness and store only a SHA-256 hash. They bind to the exact
project UID/generation, destination selector hash, owner, connection, and policy revision.
The writer repeats authorization through an uncached client immediately before compare-and-
swap publication. The public command is one-time and must not appear in logs, status, or
metrics.

Verification

`make verify-t06-core` covers policy, resolution, pinning, cleanup, registration, replay,
expiry, revoke/restore, redaction, and race behavior. `make verify-t06-kind-rbac` proves the
writer/public-receiver permission split on the development cluster. Additional kind probes
exercise mTLS and certificate rotation in the T08 path.

Remaining evidence boundary

Real Slack discovery and delivery, real PagerDuty delivery/duplicate/revoke behavior, and
real Telegram registration with public DNS and credentials are deferred. A fake local
PagerDuty fixture proves only catalog resolution and Sentry action configuration.
