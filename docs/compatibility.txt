1. Правила статуса

Verified       — выполнен реальный вызов в указанной среде и сохранён очищенный результат.
ContractTested — контракт подтверждён version-pinned исходником/официальной документацией
                 и локальной проверкой обезличенного fixture.
Unsupported    — подтверждённый контракт не позволяет сохранить обязательную семантику.
Unknown        — реальный вызов или достаточный version-pinned контракт отсутствует.

На 2026-10-30 обе self-hosted версии прошли fresh install, полные миграции, health-check,
Bearer authentication и реальный public-API lifecycle create/read/key/delete на полностью
одноразовых volumes. В 24.7.1 дополнительно подтверждено отсутствие legacy rules после
default_rules=false. В 26.10.1 GET project detectors не опубликован и отвечает 403,
поэтому эффект default_rules=false остаётся ContractTested. SaaS token отсутствует.

5. Marker strategy

Create contract 24.7.1 и 26.10.1 не имеет native label/annotation/metadata/description.
Следовательно, для project единственный source-confirmed атомарный вариант — reserved
fragment в display name при отдельном человекочитаемом slug:

  slug: checkout
  name: Checkout [managed;o=payments;m=company-sentry-op]

Форма marker означает origin=managed, o=operator-owner, m=managed-by. Parser обязан
проверять точный suffix целиком; произвольная подстрока owner не считается marker. До
POST protected binding хранит create intent, owner, manager UID, slug,
expected display name и operation hash. Lost response восстанавливается только GET по
slug + точное совпадение expected marker + pre-existing create intent. Имя без binding
не даёт ownership. Реальный lost-POST test всё ещё Unknown.

Project name в 24.7.1 и 26.10.1 ограничен 50 Unicode characters. Exact grammar probe:

  <displayName> [managed;o=<owner>;m=<manager>]

owner/manager являются lowercase human aliases с grammar
`[a-z](?:[a-z0-9.-]*[a-z0-9])?`; semantic source остаётся trusted access/connection
configuration, поэтому совпадение grammar само по себе не превращает opaque ID в alias.
Fixed overhead с одним пробелом равен 16 characters, поэтому допустимый displayName budget:

  50 - 16 - len(owner) - len(manager)

Budget обязан быть >=1. Пример занимает 49 и оставляет один character запаса. Delimiter
injection, uppercase aliases, nested marker и overflow отклоняются до POST. Команда
make verify-name-resolution проверяет formatter/parser и обязательную связку marker +
protected binding + matching manager claim. Это снимает неопределённость grammar/bounds,
но real lost-POST recovery остаётся Unknown.

Legacy issue/metric alert name и modern workflow name допускают тот же reserved suffix.
Для modern detector/workflow наличие лучшего metadata механизма пока Unknown; fallback
нельзя считать выбранным до round-trip стендового теста.

9. Telegram-source webhook

24.7.1 project service hooks создаются по readable URL и event list. Модель генерирует
secret и подписывает точный JSON body HMAC-SHA256; delivery header называется
X-ServiceHook-Signature. Worker также передаёт X-ServiceHook-Timestamp и
X-ServiceHook-GUID, timeout=5s, max_retries=5, default retry delay=5m.

Routes:
POST /api/0/projects/{org}/{project}/hooks/ — project:write, feature servicehooks required.

Source:
https://github.com/getsentry/sentry/blob/24.7.1/src/sentry/api/endpoints/project_servicehooks.py
https://github.com/getsentry/sentry/blob/24.7.1/src/sentry/models/servicehook.py
https://github.com/getsentry/sentry/blob/24.7.1/src/sentry/tasks/servicehooks.py

Это доказывает доступный cryptographic mechanism для 24.7.1 contract, но не реальную
доставку, feature enablement, retry timing и TLS behavior. Важный риск: version-pinned
worker вызывает safe_urlopen(... verify_ssl=False). До security review и реального теста
Telegram остаётся неготовым, несмотря на HMAC.

26.10.1 сохраняет тот же v0 payload family project/group/event, per-hook secret,
HMAC-SHA256 и X-ServiceHook-* headers. Source tests вычисляют подпись от того же exact
serialized body. Обезличенный version-specific fixture проходит тот же HMAC vector.

Однако modern contract не устраняет blocker:
- GET/POST/PUT/DELETE project service-hook endpoints имеют ApiPublishStatus.PRIVATE;
- projects:servicehooks имеет default=False и проверяется до list/create;
- worker по-прежнему вызывает safe_urlopen(... verify_ssl=False);
- retry policy теперь Retry(times=3, delay=5m), а не legacy max_retries=5.

Следовательно 26.10.1 cryptographic mechanism = ContractTested, но возможность создать
hook обычным supported API token, TLS security и доставка = Unknown/Unsupported до стенда
и выбранной deployment policy. Нельзя переносить legacy retry assertions на modern.
