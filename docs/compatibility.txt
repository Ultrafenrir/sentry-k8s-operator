SENTRY CONFIGURATION OPERATOR — COMPATIBILITY MATRIX
Source review: 2026-10-31
Status: Contract baseline plus recorded disposable-stack evidence; not a production or SaaS
certification.

1. Evidence labels

- `Verified`: exercised against the exact live disposable target.
- `ContractTested`: supported by version-pinned source, sanitized fixtures, and executable
  adapter tests, but not a live target.
- `Unknown`: insufficient evidence; the controller must fail closed.
- `Unsupported`: intentionally rejected by the selected adapter.

4. Project and DSN rules

Project creation omits `platform` unless the CR supplies it and sends the atomic
default-rule suppression flag. Managed creation is unavailable unless both safe-create
capabilities are present in connection status from real evidence.

The operator recovers interrupted creates through readable slug plus its exact ownership
marker. It never sends a second blind POST. It selects an active project client key and
publishes only the public DSN to the application Secret. Secret/token/private key material
does not enter status or logs.

Managed projects may attach additional authorized teams through `grantAccess`. The
controller lists project teams, pins each managed team identity, verifies add/remove
mutations, and leaves unrelated teams untouched. A clean disposable-stack run verified
grant, read-back, revoke, and preservation of the primary project team on both supported
versions.

5. Settings

Both supported versions expose compatible public filter endpoints and project settings for
the alpha PII fields, behavior fields including allowed browser origins, built-in Relay PII
rules, grouping enhancements, and fingerprinting rules.
Reconciliation writes only managed fields, reads them back, and becomes quiet after drift is
repaired. The advanced fields are rendered from bounded typed input; raw JSON and rule grammar
remain outside the public contract. Grouping profiles and secondary-grouping migration are also
excluded because 26.10.1 rejects their manual public-API mutation while 24.7.1 accepts it.
Both versions also accept the same twelve built-in symbol-source identifiers through the
project settings endpoint. Sentry 26.10.1 has an additional `proton` source and a native
source-server mapping toggle that 24.7.1 does not expose, so neither is portable. Custom
symbol sources remain outside the settings contract because their public endpoint carries
credentials and generated source identities. The separate owned-child contract supports
HTTP, S3, and GCS on both targets. It loads credentials from project-namespace Secret keys,
stores only protected exact identities and desired-state digests, repairs visible drift,
rotates credentials through a full update, and performs exact cleanup. Azure remains
excluded because 24.7.1 does not expose it.

Project quota protection has no portable public mutation contract. Sentry 24.7.1 accepts
feature-gated project `dynamicSamplingBiases`, while 26.10.1 only serializes that legacy
field and moves manual target rates to a private, organization-scoped, feature- and
sampling-mode-gated bulk endpoint that requires numeric project IDs. Both versions expose
the raw internal `quotas:spike-protection-disabled` option in detailed serialization without
a bounded typed public update contract. These controls remain unavailable. Managed client
keys already expose the separate portable count/window rate limit.

6. Alerts

The legacy adapter owns Sentry issue and metric rules using protected markers and journals.
The modern adapter owns an attached metric detector/workflow pair. Delete/disable semantics
are adapter-specific and validated before mutation. Omitted alerts remain unmanaged; an
explicit empty map cleans up only operator-owned alerts.

Direct alerts and reusable cluster-scoped alert policies have live configuration evidence
on both supported targets. Policy generation updates preserve protected child ownership and
report aggregate rollout only after policy-owned targets and alerts are Ready. This does not
prove that Slack or PagerDuty delivered a notification.

7. Integrations

Organization integrations require organization integration scopes in addition to read/write
scopes for the affected project or alert. PagerDuty public integration data contains an
account identity and a service table; the operator does not decode or expose routing keys.
No equivalent stable Slack channel enumeration contract is certified across both targets.

8. Minimum token scope intent

The local acceptance token requests organization read/write/admin/integration, member/team
read/write/admin, project read/write/admin, and alert read/write scopes because the complete
test fixture needs all of them. This is not a least-privilege SaaS recommendation. SaaS scope
minimization remains deferred and must be tested with a real account.

9. Required follow-up

Keep source fixtures pinned and sanitized, rerun disposable-stack configuration acceptance
when a supported Sentry version changes, and add SaaS only after least-privilege and behavior
acceptance. Never promote a capability solely from the server version string.
