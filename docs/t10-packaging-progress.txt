T10 — PACKAGING (PARTIAL / SOURCE-TESTED)
Date: 2026-11-01

The alpha Helm chart in `charts/sentry-kubernetes-operator` is generated from the canonical
Kustomize outputs. It contains CRDs in `crds/`, the default controller/admission resources,
five protected namespaces, and opt-in registration/monitoring payloads. Drift verification
regenerates files into a temporary chart and compares exact bytes.

Safety boundaries:

- The chart does not enforce a Kubernetes version range. Rendering is verified without a
  chart-level version gate, while runtime compatibility evidence remains limited to the
  Kubernetes 1.35/1.36 matrix documented separately.
- production=true requires a canonical sha256 image digest; development tags remain
  available only when production=false.
- registration is off by default; monitoring and public Gateway routes cannot be enabled
  without registration. Gateway rendering additionally requires an existing parent/listener
  identity and two distinct exact public hostnames.
- controller monitoring scraper access is independently opt-in. Enabling it requires
  controller monitoring plus one exact Prometheus ServiceAccount name/namespace; default
  rendering creates no scraper binding.

The corresponding persistent-kind RBAC gate creates one temporary Prometheus ServiceAccount,
verifies that the rendered binding grants only non-resource `GET /metrics` while operator
Secret reads remain denied, then removes the exact binding and namespace. This closes the
previous gap between the authenticated ServiceMonitor and its scraper authorization without
granting a wildcard group or namespace subject.

The independent `make verify-t09-kind-controller-monitoring` gate exercises the packaged
contract through official cert-manager v1.21.1 and Prometheus Operator v0.94.2 in a disposable
Kubernetes 1.35.5 cluster. Both controller targets are discovered but return HTTP 403 before
the fixed-subject binding, then recover to distinct `up=1` series through CA/hostname-verified
TLS. The exact scraper remains unable to read operator Secrets, both shipped alerts load once,
and a disposable product-metric rule reaches firing without controller or Prometheus restarts.
- cert-manager remains an explicit prerequisite; the chart does not install it.
- all five protected namespaces have `helm.sh/resource-policy: keep`. Helm uninstall may
  remove RBAC but must not remove binding/routing/queue/hook-source/audit namespaces or
  their Secrets.
- CRDs use Helm's `crds/` lifecycle and are not silently deleted/upgraded as ordinary
  templates. CRD evolution still requires the repository's explicit compatibility process.

`make verify-helm` runs drift, helm lint, CRD inclusion, default/all/production renders,
negative schema gates, Kubernetes 1.35/1.36 rendering, and package creation. A server-side
dry-run against persistent kind is recorded separately. `make helm-package` writes the
verified chart archive under ignored `dist/`.

The chart and Make deployment path share one canonical pair of Gateway API v1 TLSRoute
templates. They attach the Telegram and Sentry receivers separately to an installation-owned
TLS/Passthrough listener, preserving backend certificate termination and hot reload. Default
rendering contains no TLSRoute. Helm rejects disabled registration, missing route inputs and
duplicate SNI hostnames; the Make path also verifies the v1 CRD, listener mode, Services,
server-side schema and controller-reported Accepted/ResolvedRefs conditions. This is packaging
and source evidence only until exercised through a real conformant Gateway implementation,
public DNS and trusted certificates.

The reproducible `make verify-t08-kind-gateway-api` gate installs the pinned official Gateway
API v1.5.0 Standard CRDs into its own Kubernetes 1.35.5 kind cluster. It verified TLSRoute v1
as served/storage, accepted both rendered routes through server dry-run, rejected a
TLS-terminating listener, and removed only its probe cluster through a trap. This validates
the API contract without installing or claiming a Gateway controller/dataplane.

`make verify-t08-kind-gateway-dataplane` adds the independent real implementation check. It
builds the current operator image, installs pinned Envoy Gateway v1.9.3 with the patched Envoy
v1.39.6 proxy in a disposable kind cluster, waits for both canonical routes to report
Accepted/ResolvedRefs, and reaches the real receiver `/readyz` through SNI passthrough while
validating a backend-owned CA and hostname. Receiver pod identities/restart counts remain
stable and the probe cluster is removed. This closes local Gateway dataplane packaging
evidence, not internet-routable address, DNS, or external Sentry/Telegram acceptance.

`make verify-t08-kind-monitoring` installs official Prometheus Operator v0.94.2 in another
disposable Kubernetes 1.35.5 cluster. The canonical ServiceMonitor discovered and scraped
both worker replicas through the metrics namespace label and NetworkPolicy, the canonical
PrometheusRule loaded all three shipped alerts, and a disposable rule on the same product
metric reached firing state. No protected identity appeared in the queried series. The gate
does not claim production Alertmanager routing or notification delivery.

`make verify-samples` loads every YAML resource listed by `config/samples/kustomization.yaml`
into a real envtest API server using server-side dry-run. The test fails when a sample is
omitted from the kustomization, violates a built-in or generated CRD schema, is rejected by
admission, or bypasses the live SentryProject defaulting webhook. The same test can run in
the local Kubernetes 1.35/1.36 test matrix. The GitHub test workflow installs pinned
controller-gen and Kubernetes 1.35 envtest assets before running one `make test` job;
it does not mutate dependency files with `go mod tidy`. Public examples use readable names/slugs only; the
name-resolution contract explicitly rejects external IDs as selectors or workarounds.

`docs/quickstart.md` now gives the service owner a one-resource path containing only the
minimal managed `SentryProject`. Platform-owned connection, policy and live capability
prerequisites are separated explicitly; the guide never treats fixture evidence as proof
that a target Sentry can create a project or provide a usable DSN. The published YAML is the
same minimal contract already admitted in the real-schema sample/golden tests.

`docs/troubleshooting.md` maps the controller's emitted fixed reasons to safe operator or
service-owner actions. It directs uncertain ownership/create/delete states to the redacted
read-only admin report, never to protected Secret editing or external-ID workarounds. The
controller now emits transition-only Events from the same safe conditions without periodic
spam; the guide explicitly distinguishes them from a complete audit trail.

Clean-runner workflow contracts no longer run `go mod tidy` or download "latest" kind.
Go 1.26.10, controller-gen 0.21.0, kind 0.32.0 (binary checksum), the Kubernetes 1.35.5
node image digest, and the 1.35/1.36 envtest versions are explicit. The scaffold e2e
assertion now expects both HA controller replicas. These YAML/source changes are locally
parsed and their underlying test targets pass, but no GitHub-hosted workflow run is claimed
from this workstation.

The first isolated e2e attempt exposed two stale scaffold assumptions and was intentionally
stopped: the metrics client namespace lacked the required `metrics=enabled` label, and a
TokenRequest value was embedded in the logged `kubectl run` argument. The test now reads its
projected ServiceAccount token only inside the pod, uses non-verbose curl with bounded
connect/total time, logs only `METRICS_OK`, labels the namespace for the actual NetworkPolicy,
and always deletes the kind cluster even when the suite fails. The interrupted run is not
counted as passing evidence. A clean rerun on kind Kubernetes 1.35.5 passed the initial six specs:
two HA replicas, readiness, cert-manager certificate/CA injection, authenticated metrics
through the real NetworkPolicy, and a redacted `SecretInputInvalid` condition plus Event for
a cluster-scoped SentryConnection. The temporary cluster was deleted by the target. No
Sentry API was contacted, and this local run is not a GitHub-hosted workflow result.

The same run exposed that scaffold `deploy` targets used `kustomize edit` in the source
tree, leaving the e2e image in canonical manifests and therefore in the generated chart.
Controller and registration image rendering now happens in a temporary copy through
`hack/render-kustomize-image.sh`; deploy, installer and e2e runs no longer mutate tracked
Kustomize state. Helm drift verification caught this defect as intended.
`make verify-helm` now also renders both image overlays with a synthetic tag, checks the
expected image counts, and byte-compares the source kustomizations before and after.

A seventh e2e spec performs a real two-replica Deployment image rollout from exact baseline
commit `ba5143fa704a923e251a31c71d8f32342ba81344` to the current worktree. The baseline image
is exported from that full commit SHA into a temporary source tree; the build fails closed
when the exact commit is unavailable. The current image is built independently from the
working tree. The first rollout run had previously exposed a brief admission
connection-refused window after Kubernetes declared the rollout complete. The controller
Deployment therefore requires maxUnavailable=0, maxSurge=1 and minReadySeconds=5, and the
spec waits for its own initial rollout instead of relying on an earlier test.

Before the distinct-version rollout, an isolated fake Sentry HTTP boundary commits one real
project-create POST and then closes the connection without returning a response. The
baseline controller persists a protected `CreateProject`/`Submitted` operation and reports
`CreationOutcomeUnknown` while the committed project remains hidden. Only after the current
controller rollout is ready does the boundary expose the project. The current controller
then recovers the exact ownership marker, clears the pending operation, pins the external
identity, reaches `ProjectReady=True`, and completes Retain cleanup. The server asserts that
the create POST count remains exactly one. The same spec preserves exact bytes, labels, UID,
and immutability for the independent pending binding/journal, route, admission candidate,
and InFlight/Retry/DeadLetter fixtures, and accepts a server-side SentryProject dry-run after
the upgrade. A clean kind Kubernetes 1.35.5 run passed all 8/8 specs and deleted its exact
temporary cluster. This is local upgrade and external-operation recovery evidence against a
purpose-built fake Sentry boundary, not target Sentry, hosted release, or rollback evidence.

The eighth spec removes and reissues the cert-manager metrics Secret, waits for both
controller-runtime certificate watchers to observe the projected update, and scrapes with
the reissued CA. Both controller pod UIDs and restart counts remain unchanged. The final
suite passed 8/8. Secret projection took about one minute on the single-node test cluster;
an intentionally early probe failed TLS and is not counted as acceptance evidence. The
controller metrics manifest and e2e no longer use an implicit self-signed fallback or
`--insecure`.

`make verify-t09-kind-multinode-failover` is a separate disposable-cluster gate. It builds
the current image, creates one control-plane plus two workers, requires the two controller
replicas on distinct workers, deletes the exact Lease holder, and verifies transfer to the
existing cross-node follower while a redacted missing-Secret SentryConnection and
server-side admission remain stable. It refuses to reuse an existing cluster name and
deletes only its own cluster through a trap. This is not part of the default source matrix
and does not claim live Sentry mutation or physical node-loss acceptance.

`make verify-t09-kind-backup-restore KIND_CONTEXT=<kind-context>` is a separate bounded
recovery gate against an existing kind API server. It refuses namespace collisions, keeps
the protected bundle in memory, exercises exact deletion plus create-only/resumable restore,
and removes only four exact ownership-labeled drill namespaces. It does not publish a
plaintext backup command or claim persisted encryption, key management, audit restoration,
CR/input-Secret restoration, or a complete installation restart.

Persistent kind v1.35.5 accepted both the default chart including CRDs and the chart with
registration enabled through real server-side validation (`kubectl apply --dry-run=server`).
An SSA dry-run was intentionally not used as the acceptance result because the existing
Kustomize installation owns fields through client-side apply; those ownership conflicts are
a migration concern, not a schema failure. No Helm release was installed over the running
development installation.

`make verify-t10-failure-injection` now collects the deterministic non-live failure suite:
429 with Retry-After, 5xx backoff, header/body timeout classification, no blind retry of a
mutating POST, marker-based lost-response recovery without a second POST, competing-writer
serialization, independent component progress after partial failure, authorization changes
before mutation, two-phase DSN cutover, and preservation of a working Secret on denial. It
runs the focused packages under the race detector. The gate also drops the connection after
a modern detector POST has committed, then proves that the composite workflow/detector
identity is recovered without another workflow or detector POST; foreign ownership markers
are rejected before either child DELETE. The same gate now drops a legacy issue-rule create
response after commit and proves exact-name recovery without a second POST. All
servers/adapters are httptest or fakes; this is repeatable failure-contract evidence, not
target Sentry acceptance.

Production deploy aliases now require `cosign verify` of the exact image digest against one
exact GitHub release workflow identity at a version tag and the fixed GitHub Actions OIDC
issuer. `make verify-signature-policy` uses a fake cosign boundary to prove exact arguments
and rejection of mutable images, broad/branch identities and verification failure. The
tag-only `.github/workflows/release.yml` publishes
`docker.io/ultrafenrir/sentry-k8s-operator` with the `DOCKERHUB_TOKEN` repository secret,
uses SHA-pinned actions, minimal permissions, keyless signing of the exact pushed digest
and immediate verification of its exact workflow/tag identity; `make
verify-release-workflow` locks that source contract. No hosted
workflow run occurred and no image was pushed, signed or verified against a real registry.

This does not make T10 complete. There is no published registry/chart repository, signed
release, live Sentry alert-action acceptance, human usability test, or hosted upgrade and
rollback evidence.
