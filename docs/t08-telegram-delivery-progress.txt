T08 — TELEGRAM HOOK INGRESS AND DELIVERY
Updated: 2026-10-31
Status: Contract-tested durable core and kind dataplane; real Telegram delivery is deferred

Queue and worker

The delivery namespace stores an at-least-once Kubernetes-backed queue. Object names contain
only canonical hashes. Records use deterministic dedupe, content-hash conflict detection,
conservative capacity checks, ResourceVersion compare-and-swap claims, expiring leases,
bounded exponential retry, dead letters, and exact retention deletion.
Retention deletion is audit-gated: expired admission candidates, sent tombstones, and dead
letters are preserved when the immutable audit sink is unavailable, and each attempted
deletion records only a fixed local resource, queue revision, and closed outcome enums.

Admission uses an immutable candidate Secret followed by a deterministic final record so the
producer needs create/delete but not update/patch. Lost final-create responses are recovered
by reading the committed record. Abandoned candidates are bounded and janitor-cleaned.

After success, route and payload data are removed and only a dedupe tombstone remains. Dead
letters retain a protected payload until their separate retention boundary. Secrets require
Kubernetes encryption at rest. Exactly-once delivery is not promised: a Telegram success
followed by a failed completion CAS can be sent again after lease recovery.

Telegram adapter

The adapter sends numeric chat/topic identity and bounded plain text without parse mode,
disables link preview, and limits response bodies. HTTP 429 honors bounded `retry_after`;
transport and 5xx failures retry; permanent 4xx and invalid routes go to the dead-letter
state. Errors exclude bot token, route, target, response body, and message.

The worker reloads the projected bot token before every operation. Invalid rotation makes
readiness fail while liveness remains healthy. Two replicas and a PodDisruptionBudget are
published. The worker has no Sentry credential or project-binding access.

Authenticated hook path

The public Sentry hook receiver validates exact method/path/media type, bounded body,
single signature/timestamp/GUID headers, clock skew, and HMAC-SHA256 before JSON parsing.
It maps the authenticated source to local renderer input and passes only canonical hashes
through a signed TLS 1.3 internal handoff.

The receiver has no Kubernetes API token. It reloads bounded source configuration for every
request. HMAC rotation supports exactly one active key or a two-key old/new overlap and
checks both without early exit. The internal producer reloads its trust bundle on each
handshake and creates queue records through a protected source-to-route resolver.

The project controller now owns the matching Sentry project service hook. It journals a
create before the Sentry call, recovers a lost create response by listing only the exact
opaque source endpoint, rejects duplicate matches, and pins the returned hook identity and
a one-way secret fingerprint in protected project state. Both supported Sentry versions
expose active-on-create hooks even when `isActive=false` is requested. Initial creation
therefore uses a deterministic unpublished staging URL, publishes the protected source plan
and verifier key, moves the exact hook to the real receiver URL, and independently reads it
back.
Observed secret changes use an old/new verifier overlap before the new key is retired.
Increasing the monotonic `serviceHookRevision` creates the replacement at its deterministic
unpublished staging URL, publishes the old/new verifier overlap, moves and reads back the
replacement at the real receiver, deletes only the pinned old hook, and then retires the old
key. A receiver URL change is admitted only with a larger revision. Interrupted rotations
finish their durable target before starting a later requested revision.
Removal disables public verification, deletes the protected source, deletes only the pinned
hook identity, and verifies absence before releasing the binding. The generated Sentry
secret is never accepted through the public API or copied to public status.

Rendering and privacy

Messages are generated only from local project, alert, environment, and fixed severity
values. Event payload, title, URL, user/request data, stack trace, external IDs, and raw
Sentry body are not renderer inputs. Metrics contain no project, route, chat, record, or
payload labels.

Verification

`make verify-t08-core` covers queue failure windows, concurrency, retry, dead letters,
fail-closed audited retention, hook validation, HMAC rotation, internal signatures, rendering, redaction, and
Secret rotation. Unit and envtest coverage now also exercise service-hook HTTP contracts,
lost-response recovery, active-on-create staging publication ordering, protected identity pinning,
observed HMAC change overlap, proactive replacement rotation, queued-revision recovery,
exact removal, and controller wiring. Dedicated kind targets cover CA rotation, Gateway API
TLS passthrough, Prometheus discovery/rules, and queue soak behavior.

Remaining evidence boundary

Real Telegram send/retry/dead-letter behavior with bot/chat/topic credentials, public DNS,
publicly trusted certificates, externally reachable ingress, and production Alertmanager
routing are deferred. The existing tests prove local protocol and dataplane behavior only.
The project service-hook API create/read/update/delete shape and its active-on-create behavior
were live-accepted on Sentry 24.7.1 and 26.10.1 without sending a notification. Full-controller
runs on both versions then proved staging publication, protected identity pinning, mutation-free
convergence, revision-triggered replacement, old-hook cleanup, protected-secret redaction, and
exact final removal. Failure-window recovery retains local unit and envtest evidence; external
delivery remains deferred.
