T08 — TELEGRAM RECEIVER И DELIVERY (IN PROGRESS / CONTRACT-TESTED CORE)
Дата: 2026-10-30

1. Что реализовано

- Kubernetes-backed at-least-once queue в отдельном
  sentry-kubernetes-operator-delivery namespace. Dedupe key и route key — только
  canonical SHA-256; chat/topic identity и message text не попадают в object metadata.
- Идемпотентный Enqueue, конфликт при повторном dedupe key с другим content hash,
  консервативный admission capacity check, ResourceVersion CAS claim, lease expiry
  reclaim, bounded exponential retry, DLQ и retention sweep exact-delete.
- Admission выполняется через отдельный immutable candidate Secret: producer использует
  только create/delete, после capacity List создаёт детерминированную final запись и затем
  exact-delete кандидата. Worker видит только final `telegram-delivery` records. List/delete
  outage оставляет bounded, resumable и не claimable candidate; identical enqueue
  продолжает тот же intent, потерянный ответ final Create распознаётся чтением committed
  записи, а janitor удаляет только истёкшие abandoned candidates. Это закрывает API-server
  failure window без выдачи producer прав update/patch и без удаления admitted Pending work.
- После успеха payload и route key удаляются из записи; остаётся только dedupe tombstone
  с content hash до окончания retention. DLQ сохраняет защищённый payload до отдельной
  retention границы. Queue хранится в Secret и требует encryption-at-rest от установки.
- Worker не обещает exactly-once: если Telegram принял запрос, а CAS Complete не прошёл,
  lease recovery может повторить отправку. Это явно проверенная at-least-once граница.
- Telegram sendMessage adapter отправляет числовые chat_id/message_thread_id и plain text
  без parse mode, отключает link preview, ограничивает текст 4096 Unicode code points и
  response body. 429 учитывает bounded retry_after; 5xx/transport повторяются; 4xx и
  invalid route идут в DLQ. Bot token, URL, response body, target и message не входят в
  возвращаемые ошибки.
- Bot token перечитывается из projected Secret перед каждой отправкой. Worker readiness
  меняется на 503 при невалидной ротации, liveness остаётся отдельным /healthz.
- Worker имеет две реплики и PDB. Он не имеет Sentry credentials и project/binding RBAC.
  В routing namespace у него только get Secret; в queue namespace — get/list/update/delete
  без create. Отдельный producer имеет get source и необходимые для идемпотентности/
  backpressure get/list/create/delete queue, но не update/patch. Registration
  writer/controller пишут route records в третьем изолированном
  sentry-kubernetes-operator-routing namespace.
- Egress worker ограничен DNS и TCP/443; Telegram Bot API и Kubernetes API используют 443.
- Source-derived service-hook verifier проверяет exact path/method/media type, bounded raw
  body, single signature/timestamp/GUID headers, clock skew и HMAC-SHA256 до JSON parsing.
  Он сверяет signed project slug с локально настроенным source binding и передаёт sink
  только этот local binding key и SHA-256 dedupe key от local source + authenticated event
  ID; raw body, event ID, issue title, URL
  и tags не входят в envelope.
- PII-minimal renderer строит bounded plain text только из локальных project/alert/
  environment names и фиксированной severity. У него намеренно нет входа для event body,
  issue title, URL, user/request/stack trace или external ID.
- Producer-core получает source-to-route deliveries только через protected resolver,
  валидирует и рендерит весь batch до первой записи, сортирует routes и выводит отдельный
  canonical dedupe key на route. После частичного enqueue повтор использует те же ключи,
  поэтому уже записанные items идемпотентны, а оставшиеся можно безопасно продолжить.
- Durable source resolver теперь хранит отдельный revisioned CAS record в изолированном
  `sentry-kubernetes-operator-hook-sources`, а не в общем binding state. Ключ и route keys
  должны быть canonical SHA-256, deliveries строго отсортированы и уникальны, renderer
  input проходит полную валидацию до записи. Source identity/project slug нельзя изменить
  CAS update: для этого нужен новый source key. Запись включена в semantic backup/restore,
  а admin-report выводит только aggregate count. Controller publication этого record и
  синхронизация public source config остаются следующим wiring-подэтапом.
- Internal producer handoff теперь имеет отдельный closed endpoint
  `/internal/v1/sentry-hooks/deliveries`: принимает только canonical source/dedupe hashes,
  exact POST/JSON без query/encoding/unknown fields, verified TLS 1.3 client certificate с
  точным URI SAN и ECDSA/Ed25519/RSA-PSS подпись exact method/path/operation/body hash.
  CommonName и proxy identity headers игнорируются. Public-side client отклоняет не-HTTPS
  URL и любой ответ кроме 204; response body bounded/discarded. Producer опубликован как
  HA workload с отдельным health port, PDB, server certificate и NetworkPolicy.
- Internal producer перечитывает client CA bundle на каждом TLS handshake, а public
  receiver перечитывает producer CA и client leaf на каждом новом соединении. Внутренний
  transport намеренно не использует proxy и keep-alive: projected old+new trust overlap,
  cutover leaf и удаление old CA начинают действовать без restart; malformed replacement
  bundle fail closed для нового handshake.
- Tokenless public `sentry-hook-receiver` опубликован отдельным HA workload без Kubernetes
  API token/RBAC. Он выбирает source только по canonical hash в `/events/<hash>`, на каждый
  запрос строго перечитывает bounded JSON из projected admin Secret, проверяет Sentry HMAC
  и передаёт producer только два hash через подписанный mTLS handoff. Public TLS, source
  Secret, Ingress/Gateway и DNS остаются ответственностью установки; receiver egress
  разрешён только к producer и DNS.
- Projected verifier config принимает ровно один active HMAC secret либо bounded overlap
  из old+new во время ротации. Оба canonical-base64 ключа проверяются без раннего выхода;
  пустой, повторяющийся или третий ключ fail closed. После переключения Sentry старый ключ
  удаляется из массива без restart/token/RBAC у receiver.
- Rotation planner строит отдельные overlap и retired payload: из одного текущего ключа
  получается old+new перед внешним переключением и только new после его независимой
  проверки. Повторный reconcile и rollback к одному из двух ключей идемпотентны, а попытка
  добавить третий параллельный ключ fail closed; payload всегда заново проходит строгую
  verifier validation.
- Resumable rotator применяет этот план через byte-exact CAS одного aggregate entry:
  overlap публикуется до idempotent external switch+independent verify, retired payload —
  только после подтверждения. Ошибка switch/verify или финального CAS оставляет old+new;
  повторный reconcile безопасно завершает тот же intent, а stale/third-key plan не делает
  внешний вызов. Конкретный Sentry adapter всё ещё gated T07 live API evidence.
- Receiver readiness отдельно перечитывает все visible projected entries: malformed key,
  filename или JSON дают bodyless 503 на `/readyz`, но `/healthz` остаётся 200 и не создаёт
  restart-loop. Пустой aggregate Secret допустим до появления первого alert source.
- Publication core выводит opaque source key только из Kubernetes connection/project UID,
  формирует exact `<receiverURL>/events/<hash>` без external ID и обновляет один entry в
  заранее созданном aggregate Secret через resourceVersion CAS, сохраняя siblings. Порядок
  fail-closed: protected source создаётся/обновляется до public verifier entry; при удалении
  verifier entry exact-delete выполняется раньше protected source. Ошибка между шагами
  оставляет безопасное resumable состояние, а отсутствующий admin Secret не создаётся
  controller-ом самовольно. Реальное controller alert wiring всё ещё gated T07 API/adapters.
  Real envtest API-server round-trip дополнительно моделирует overlap rotation между
  publish и stale cleanup: byte-different verifier entry блокирует unpublish и сохраняет
  protected source; exact retry удаляет только свою пару и не меняет sibling entry.
- Worker публикует отдельный `/metrics` endpoint с fixed-enum counters для sent/retry/
  dead-letter/error, processing histogram, aggregate queue records по fixed state, age
  oldest outstanding и refresh-error counter. Метрики не принимают project/route/chat/
  record/payload/upstream-error labels. Scrape ingress разрешён только namespace с label
  `metrics: enabled`; health остаётся на отдельном порту.
- Внешний `sendMessage` окружён закрытым audit-контрактом. До сетевого вызова worker обязан
  записать `delivery/deliver/started`; после ответа — только фиксированный accepted/failed
  outcome. Audit event содержит constant local resource и queue revision, но не dedupe/route
  hash, record name, chat/topic, message, token или raw error. Недоступный sink до Send
  блокирует сеть и оставляет InFlight claim для lease recovery. Недоступный sink после 2xx
  не выполняет Complete, поэтому честно сохраняет уже заявленную at-least-once границу.
- Optional `config/registration-monitoring` содержит ServiceMonitor и PrometheusRule для
  queue age >5m, новых dead letters и metrics refresh failures. Он не входит в default
  install: make target сначала требует обе Prometheus Operator CRD, а operator-specific
  discovery labels должны добавляться installation overlay.

2. Контракты и источники

Официальный Telegram Bot API sendMessage задаёт chat_id, optional message_thread_id и
text 1–4096 characters after entities parsing:
https://core.telegram.org/bots/api#sendmessage

Официальный ResponseParameters.retry_after задаёт число секунд flood-control ожидания:
https://core.telegram.org/bots/api#responseparameters

Адаптер намеренно не использует новые rich/ephemeral возможности и не принимает raw
Telegram payload от пользователя.

3. Проверки

- make verify-t08-core: race queue/client/worker/health tests, go vet, three-namespace
  isolation, worker RBAC, probes, PDB и NetworkPolicy manifest contracts;
- make verify-t08-kind-ca-rotation: isolated old CA -> overlap -> new CA internal mTLS и
  independent public receiver CA/leaf cutover на persistent kind без изменения pod
  template во время cutover; old public trust отклоняется после смены leaf, probe cleanup
  возвращает canonical cert-manager/admin Secrets и удаляет только собственные records;
- make verify-t08-kind-queue-soak: bounded 128-event/16-concurrent signed public ingress
  burst через реальные receiver/producer и Kubernetes API; требует пустую probe queue,
  проверяет final revision/state, zero admission candidates/raw event-ID leaks/restarts и
  exact-name cleanup;
- queue tests: duplicate/conflict, immutable create/delete-only admission candidate,
  post-candidate List/delete failure и resumable retry, lost final-Create response,
  capacity rejection cleanup, retry due time, max-attempt DLQ, payload-free success
  tombstone, retention sweep, expired lease и stale completion;
- client tests: numeric target JSON, disabled link preview, 429 retry clamp, 4xx/5xx,
  transport/token/response non-leak и invalid input before network;
- redirect fail-closed: стандартный HTTP redirect отключён внутри adapter, чтобы Bot API
  token из URL path не мог попасть на другой endpoint;
- worker tests: success, idle, revoked route DLQ, Telegram retry_after, bounded backoff и
  crypto jitter bounds. Отдельная failure injection проверяет границу после Telegram 2xx:
  первый Complete получает ошибку Kubernetes, после lease expiry тот же item reclaim-ится,
  отправляется второй раз и только затем становится payload-free Sent tombstone;
- audit failure injection отдельно доказывает zero-send/zero-settlement при недоступном
  start event и zero-settlement после принятого Telegram 2xx, когда success event записать
  нельзя. Sentinel JSON не содержит message, route/dedupe hash или chat/topic identity;
- real envtest API-server probe сначала заполняет queue до 12 records, затем запускает 48
  одновременных unique producers. Все overflow requests получают ErrBackpressure, каждый
  rejected Secret отсутствует после exact resourceVersion cleanup, исходные 12 records
  остаются, а их повторный Enqueue идемпотентен. Probe входит в matrix 1.35/1.36 и race run;
- protected-state backup envtest экспортирует одним integrity-checked bundle binding/claim,
  Submitted journal, immutable challenge/route, immutable admission candidate и queue
  InFlight/Retry/DLQ, удаляет records и восстанавливает их create-only. Повтор
  идемпотентен; tamper, extra/changed record и unknown Secret fail closed. Bundle
  чувствительный и требует внешнего шифрования;
- service-hook tests прогоняют fixtures 24.7.1/26.10.1, auth-before-parse, tamper/skew,
  duplicate headers, secret rotation, size limit, sink retry и стабильный dedupe при
  изменённом unsigned GUID header; renderer tests отклоняют controls/unbounded fields.
- producer tests проверяют protected resolver boundary, deterministic multi-route batch,
  partial failure retry с теми же dedupe keys и zero-write при duplicate/invalid route или
  невалидном локальном render input. File-source tests проверяют strict unknown-field
  rejection, traversal/invalid hash, per-request secret rotation и отсутствие утечки.
- metrics tests подставляют неизвестные outcome/error strings и подтверждают их clamp к
  fixed `error`/`unknown`, aggregate queue state/age и отсутствие sensitive sentinels;
  endpoint tests требуют exact bodyless GET `/metrics` без query.

4. Evidence boundary и оставшаяся работа

Это ContractTested core, не live Telegram acceptance. Настоящий Bot token и test chat не
доступны; в kind применялся только синтаксически валидный локальный token, sendMessage не
вызывался. Public receiver и internal producer теперь имеют binaries/manifests и
source-tested contracts, но controller ещё не публикует согласованную пару protected
source plan + projected public verifier config. Поэтому opt-in worker без ручного source
provisioning по-прежнему видит пустую queue.

Duplicate budget намеренно не выражен ложным фиксированным числом. На один успешный claim
приходится не более одного sendMessage, но ошибка/неопределённый результат Complete оставляет
lease, и каждый следующий expiry допускает ещё одну отправку. При повторяющихся settlement
failures глобального верхнего предела дублей нет; операционная граница — lease duration,
здоровье Kubernetes API и alert на queue age. Exactly-once без идемпотентности Telegram API
не заявляется.

Project service-hook HMAC покрывает raw body, но не timestamp/GUID headers. Поэтому dedupe
никогда не зависит от этих изменяемых headers или смены HMAC key: он стабилен по local
source binding и event ID из проверенного signed body. Clock skew отсекает обычные stale deliveries, но сам по себе не
останавливает атакующего с captured body/signature и новым timestamp. Durable dedupe и
retention остаются обязательными, а source mechanism не получает завышенного replay claim.
