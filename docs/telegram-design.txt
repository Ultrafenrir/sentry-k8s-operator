SENTRY CONFIGURATION OPERATOR — TELEGRAM DELIVERY DESIGN
Updated: 2026-10-31
Status: Design and source/kind contract; production delivery not yet accepted

1. Sentry source authentication

The selected source contract uses a per-hook HMAC secret over the raw bounded request body,
plus strict timestamp and event GUID validation. The receiver authenticates before parsing
JSON and binds the signed project slug to a locally configured source plan. Provider payload
destinations are never trusted.

Sentry generates this HMAC secret. The public connection API therefore supplies only the
receiver base URL and the Telegram bot-token reference; it does not accept a fictitious
user-selected service-hook secret. The controller reads the generated secret only through
the authenticated Sentry hook API and publishes it directly to isolated verifier state.

The platform may increment `serviceHookRevision` to request a proactive replacement without
exposing secret material. The revision is monotonic, and changing the receiver URL requires
an increment. Rotation creates the replacement disabled, overlaps both verifier keys before
activation, independently reads back the active replacement, deletes the pinned old hook,
and retires the old key last. Durable protected state resumes an interrupted target before
processing a later revision.

Sentry 24.7.1 and 26.10.1 source expose compatible v0 hook payload and HMAC mechanisms, but
endpoint availability can be private or feature-gated. The operator therefore treats source
configuration as an explicit deployment capability rather than assuming it from version.

2. Public receiver validation order

1. Require exact HTTPS endpoint, POST method, path, media type, and no unexpected query.
2. Enforce body/header limits and single required headers.
3. Validate timestamp skew and canonical source identity.
4. Reload the configured one-key or two-key rotation set.
5. Verify all candidate HMAC keys without early exit.
6. Parse the bounded JSON and match the authenticated project slug.
7. Derive canonical source/event hashes and hand off only those hashes internally.

Malformed input fails closed with bounded, non-reflective errors.

3. TLS and deployment boundary

The public receiver owns its TLS endpoint and supports certificate reload. Gateway API
TLSRoute passthrough is the supported optional attachment because it preserves receiver-side
authentication and reload behavior. The repository does not create a GatewayClass, public
listener, public address, DNS record, or publicly trusted certificate.

4. Registration plane

A service owner requests a one-time registration command through a Kubernetes-authenticated
endpoint. SubjectAccessReview checks exact update permission on the selected project. The
challenge stores only a hash and binds to project UID/generation, destination, owner,
connection, policy revision, and expiry.

The user sends the command to the bot in the intended chat/topic. A tokenless public receiver
validates the Telegram secret header and forwards numeric identity over mTLS to an internal
writer. The writer repeats the fence checks through an uncached Kubernetes client and
publishes the protected route with compare-and-swap semantics.

5. Delivery plane

Authenticated Sentry events resolve a protected source plan to local route keys. A
PII-minimal renderer creates bounded plain text using only local names and fixed severity.
The producer enqueues deterministic per-route records. Isolated workers claim records,
resolve protected numeric routes, send through Telegram Bot API, and complete, retry, or
dead-letter them.

6. Durable storage decision

The alpha uses Kubernetes Secrets in a dedicated namespace for the bounded at-least-once
queue. This preserves native RBAC, compare-and-swap, backup, and encryption-at-rest
requirements without introducing an additional database. Capacity is deliberately bounded;
high-volume production use may require a future external queue adapter.

7. Evidence boundary

Fixtures, source tests, envtest, and kind prove validation, rotation, mTLS handoff, queue
semantics, privacy, Gateway passthrough, and monitoring. They do not prove public reachability
or that Telegram accepted a real message. Real bot/chat/topic delivery is deferred by the
repository owner.
