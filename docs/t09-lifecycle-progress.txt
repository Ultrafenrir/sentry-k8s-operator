T09 — LIFECYCLE, SECURITY, HA И RECOVERY (PARTIAL / SOURCE-TESTED)
Дата: 2026-10-30

Реализовано и проверяется текущей матрицей:

- controller manager рендерится с 2 replicas, Lease leader election, readiness/liveness,
  graceful controller-runtime shutdown, preferred cross-node anti-affinity и policy/v1
  PDB minAvailable=1. Отдельный three-node kind probe требует размещение replica на двух
  разных workers, удаляет exact leader pod и проверяет transfer к уже живому follower;
- default installation теперь действительно включает ingress NetworkPolicy для webhook и
  metrics, а opt-in registration layer имеет отдельные writer/receiver policies;
- controller, admission, registration writer и public Telegram receiver разделены:
  receiver не монтирует ServiceAccount token и не имеет RBAC, writer не получает Sentry
  token, protected state отделён от namespace platform credentials;
- Telegram delivery worker также отделён: routing, mutable queue и project bindings лежат
  в трёх namespaces; worker может только get routing record и CAS/list/delete queue, но не
  create queue, delete route, читать binding/credential Secret или SentryProject;
- periodic success, component retry, delete progress и registration recovery используют
  bounded ±10% jitter; ошибка entropy возвращается к base interval, а не tight loop;
- orphaned expired registration indexes очищает только leader manager bounded batch с
  jitter и exact ResourceVersion delete; registration writer сохраняет exact-get RBAC без
  list/watch;
- legacy route records из прежнего state namespace переносятся leader-only в routing через
  publish-before-delete; destination conflict/malformed source fail closed и не удаляются;
- Retain удаляет finalizer без Sentry API, DeleteProject не проходит без live authorization
  и ownership evidence, delete обрабатывается до paused;
- manager claim/handoff, protected bindings, operation journals, DSN cutover, Telegram
  PendingPublish/PendingFenceRelease и route revoke/restore используют CAS/idempotency;
- registration pending recovery выполняется direct client до Sentry dependencies;
- standalone registration probes выполняют полный HTTPS /healthz request вместо TCP
  connect, поэтому readiness также проверяет динамически загружаемый server certificate и
  не генерирует постоянный TLS handshake EOF noise;
- registration server/client leaf certificates reload на каждом handshake: kind rotation
  revisions 1->2->3 прошла с receiver->mTLS writer 204 и нулевыми pod restarts; CA trust
  overlap остаётся отдельной незакрытой границей;
- policy revoke сохраняет pinned destination identity; Telegram route exact target сначала
  отзывается и лишь затем binding фиксирует RouteRevoked; Active reconcile verify/repair
  закрывает crash window внешняя mutation -> binding CAS.
- `kubectl sentry admin-report` читает protected state в read-only режиме и выводит только
  локальные имена, фиксированные фазы и агрегаты; тесты с sentinel external ID/chat ID/event
  payload/operation key подтверждают их отсутствие в JSON. Alert bindings представлены
  только total/enabled/disabled/tombstone counts; external identity/trigger/key скрыты.
  Команда не имеет repair/delete.
- SentryConnection/SentryProject публикуют Normal/Warning Kubernetes Events только при
  изменении status/reason/fixed redacted message условия; periodic reconcile без перехода
  не создаёт event spam. Raw error/response никогда не передаётся Event recorder. Это
  transition context, а не полный audit trail.
- controller публикует product-specific `sentry_operator_reconciles_total`,
  `sentry_operator_reconcile_duration_seconds` и
  `sentry_operator_condition_transitions_total`. Все labels закрыты фиксированными
  controller/outcome/condition/status enum; namespace, resource name, Sentry identity,
  reason/message и raw error не принимаются metrics API. Unknown значения clamp-ятся к
  `unknown`, отрицательная duration к нулю, а condition counter растёт только вместе с
  уже deduplicated condition transition. Помимо source/race tests, обновлённый локальный
  image прошёл authenticated kind scrape с CA+hostname verification: видны reconcile
  duration/count, success/requeue и CredentialsReady/False transition без dynamic labels.
- optional `config/controller-monitoring` и Helm `controllerMonitoring.enabled` добавляют
  ServiceMonitor с bearer auth, exact service DNS и `ca.crt` verification без insecure TLS,
  а также fixed-label alerts на reconcile errors и burst False transitions. Установка
  fail-fast проверяет обе Prometheus Operator CRD и оставляет discovery labels overlay-у.
  Отдельный opt-in controller-monitoring access renderer/Make target/Helm values требуют
  exact Prometheus ServiceAccount name+namespace, проверяют существование SA и metrics-reader
  ClusterRole и создают только fixed-subject binding; default render доступ не выдаёт.
  `make verify-t09-kind-monitoring-access` в persistent kind создал временный exact SA,
  подтвердил `GET /metrics=yes` и `get Secrets=no`, проверил точный subject/roleRef и удалил
  binding+namespace; все controller/registration Deployment остались 2/2 Ready.
  Независимый `make verify-t09-kind-controller-monitoring` поднял disposable Kubernetes
  1.35.5 с cert-manager v1.21.1 и Prometheus Operator v0.94.2: оба CA/hostname-verified
  controller target сначала были `down` с HTTP 403 и `GET /metrics=no`, затем один exact
  binding восстановил обе серии `up=1`, не дав SA читать operator Secrets. Prometheus
  получил product reconcile metric, загрузил оба штатных alert rule и перевёл временное
  правило на этой метрике в firing; controller остался 2/2 Ready с restartCount=0, а
  временный кластер удалён;
- legacy scaffold path `config/prometheus` больше не содержит небезопасный
  `insecureSkipVerify: true`: даже этот opt-in render требует exact service DNS и `ca.crt`.
  Default comment теперь направляет в полный `controller-monitoring` overlay с alerts;
- real envtest API-server load probe создаёт burst из 40 SentryConnection с отсутствующими
  credential Secrets и одновременно запускает reconcile. Все 40 за bounded 30s получают
  redacted CredentialsReady=False/SecretInputInvalid и requeue, а fixed-label counters
  получают ровно 40 reconcile и 40 condition transitions. Probe проходит race и matrix
  1.35/1.36; это контролируемый thundering-herd contract без Sentry HTTP, не production soak.
- versioned protected-state backup core атомарно по смыслу объединяет state/hook-source/routing/delivery:
  deterministic per-record и bundle SHA-256, create-only resumable restore, отказ при
  unknown/tampered/extra/different Secret. Real envtest round trip сохраняет binding/claim,
  alert child с adapter pin/marker/hash, pending journal, immutable route/challenge и
  InFlight/Retry/DLQ. Он не выдаёт ownership,
  а production encryption и CR/input-Secret orchestration остаются обязанностью установки;
- protected operation journal принимает только Planned -> Submitted -> Verified/Failed,
  запрещает смену kind/local resource и desired hash у Submitted intent; новый intent можно
  начать только после terminal phase. Stale revision и неизвестная phase fail closed;
- внутренний alert lifecycle теперь связывает этот journal с закрытым identity-free audit
  событием до внешнего Apply и после verified/recovered/failure outcome. Audit outage до
  Apply блокирует adapter call и сохраняет Submitted intent; событие не может содержать
  external ID, desired hash, payload или raw error. Это source/race-tested alert core, но
  ещё не полный audit всех компонентов;
- Managed project create/delete теперь используют тот же fail-closed audit boundary: start
  фиксируется после Submitted и до POST/DELETE, verified outcome — до очистки pending state.
  Sink outage после успешного внешнего ответа восстанавливается marker/NotFound observation
  как Recovered без второго POST/DELETE; ReadOnly и Retain внешних вызовов не делают;
- Telegram worker тем же закрытым audit sink ограждает внешний sendMessage: sink failure до
  вызова даёт zero-send, а failure после 2xx оставляет InFlight claim для at-least-once lease
  recovery вместо ложного Sent. Event не принимает queue hashes, record/chat/topic/message,
  token или raw error; race tests фиксируют обе crash-boundary;
- Telegram registration пишет closed audit start до status fences, target CAS и immutable
  route publish. Outage до start не меняет ни один ресурс; outage после route publish
  сохраняет PendingFenceRelease, а Resume завершает тот же route с outcome Recovered.
  Code/hash, chat/topic, outbox/route key, policy resourceVersion и raw errors отсутствуют;
- Telegram destination cleanup пишет closed audit до exact-target route revoke и после
  подтверждённого delete. Outage до start даёт zero mutation; outage после delete оставляет
  binding незавершённым, а повторный RouteStore NotFound превращается в Recovered до
  RouteRevoked CAS. Audit shape не принимает target, route key или raw error;
- все эти события теперь сериализуются до mutation в отдельном protected audit namespace:
  один immutable Secret на событие, create-only права у registration writer и delivery
  worker; fail-closed ValidatingAdmissionPolicy запрещает любой UPDATE такой записи даже
  субъекту с более широкими Secret permissions. Leader-only janitor немедленно и
  затем с bounded jitter удаляет не более 100 записей старше 30 дней за проход; до первого
  delete он валидирует весь набор. `kubectl sentry audit-export` сортирует валидированные
  события по времени и не выводит Secret metadata; одна повреждённая запись даёт zero
  partial output. Unit/race и RBAC/render gates покрывают contract, kind acceptance ниже;
- backup export дополнительно прогоняет owning-subsystem semantic validators для
  binding/claim/journal/challenge/route/delivery: корректная SHA-256 не маскирует
  повреждённый alert pin/marker, target, queue state или неизвестную journal phase;
- controller Deployment закрепляет RollingUpdate maxUnavailable=0, maxSurge=1 и
  minReadySeconds=5. Kind image-rollout test делает upgrade и rollback, сохраняет живой
  SentryConnection, семь pending/routing/delivery records и повторно проверяет admission
  после каждой смены обеих replica;
- metrics endpoint использует общий cert-manager leaf с service DNS вместо runtime
  self-signed fallback. E2E проверяет CA без insecureSkipVerify; после удаления Secret обе
  replica hot-reload новый leaf через controller-runtime watcher, повторный scrape проходит,
  pod UID и restartCount не меняются;
- release build target требует versioned non-latest tag, Buildx SBOM + max provenance,
  push metadata с canonical image digest; production deploy aliases fail closed без exact
  repository@sha256. Builder Go 1.26.10 и distroless runtime также закреплены exact OCI
  index digests, а release target отклоняет mutable overrides. Production aliases теперь
  дополнительно требуют успешный `cosign verify` exact digest с exact GitHub release-workflow
  identity и фиксированным OIDC issuer; fake boundary проверяет отказ для mutable image,
  broad/branch identity и verification failure. Tag-only GitHub workflow с SHA-pinned
  actions, минимальными permissions, keyless signing exact digest и немедленной проверкой
  exact workflow/tag identity закреплён отдельным source gate. Hosted workflow run,
  registry push/signing/real verification не выполнялись локально.
- generated Helm chart сохраняет canonical Kustomize payloads с drift check, рендерится
  для Kubernetes 1.35/1.36, требует digest при production=true и keep-аннотации на всех
  protected namespaces; default и registration renders прошли kind server dry-run.

Эти пункты не означают T09 Complete. Остаются:

- multi-node failover с живыми Sentry mutations и registration traffic; cross-node
  controller Lease transfer без внешнего HTTP уже проверен;
- единый формализованный ObserveLocal -> Authorize -> ObserveExternalAllowed -> Normalize
  -> Plan -> Journal -> Apply -> Verify -> Report для всех компонентов;
- alert ingress, production encrypted backup orchestration и реальный upgrade/rollback
  между разными code/schema versions с внешне отправленными pending operations; защищённые
  локальные records уже прошли API-server backup round trip и same-commit rollout/rollback;
- authenticated admin break-glass/orphan mutation, включая legacy Telegram binding без
  route key; read-only redacted inventory и boundary runbook уже есть;
- audit для queue administration и large/long-running production soak; durable immutable
  Kubernetes retention/export, закрытые project/alert mutation, Telegram registration,
  Telegram route cleanup и внешняя delivery audit boundaries уже source-tested;
  Slack/PagerDuty cleanup ждёт
  реальных adapters;
  low-cardinality product metrics, защищённый runtime endpoint и безопасные
  transition-only Events уже реализованы, bounded API-server herd проверен; отдельный
  Prometheus Operator kind gate обнаружил обе delivery worker replica, загрузил shipped
  rules и подтвердил firing disposable product-metric alert;
- hosted release-workflow execution, real registry signature verification, chart publication
  и release upgrade acceptance; tag-only signing workflow, verification policy,
  base/builder pinning, SBOM/provenance, digest gates и generated Helm packaging уже
  source/kind-tested;
- conversion webhook только при появлении второй storage version; alpha пока намеренно
  использует conversion.strategy=None.
