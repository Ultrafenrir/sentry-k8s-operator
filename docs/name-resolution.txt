SENTRY CONFIGURATION OPERATOR — NAME RESOLUTION CONTRACT
Date: 2026-10-29

1. Algorithm

Every readable external reference follows the same fail-closed algorithm:

1. Search only inside the selected connection, organization, and allowed policy scope.
2. Require exactly one canonical name or slug match.
3. Return `ReferenceNotFound` for zero matches.
4. Return `ReferenceAmbiguous` for multiple matches.
5. Store the selected external identity only in protected internal state.
6. On later reconciles, verify the pinned identity and readable name.
7. Never switch automatically to a same-name replacement.

Status contains readable names and fixed reasons, not private IDs.

2. Resolution scopes

| Reference | Readable selector | Search scope | Duplicate behavior |
| --- | --- | --- | --- |
| Team | slug or exact name | connection organization | ambiguous |
| Existing project | slug | connection organization | ambiguous |
| Client key | configured key name or active default | exact project | ambiguous or policy error |
| Slack channel | workspace + channel without leading `#` | exact integration account | ambiguous |
| PagerDuty service | account + service | exact integration account | ambiguous |
| Telegram target | local registration name | exact project binding | registration required or ambiguous |

Telegram resolution is registration-only in the current alpha. `AlertSpec.notify` accepts
only Slack and PagerDuty references until an authenticated alert-firing source can preserve
trigger semantics.

3. Rename and replacement behavior

An external rename produces `ExternalNameChanged`; the operator does not silently rewrite
the CR. A same-name delete/recreate produces an identity mismatch. An explicit selector
change authorizes a fresh resolution and compare-and-swap rebind only after policy checks.

4. Required negative tests

Tests cover zero and duplicate matches, whitespace/case normalization rejection, leading
Slack `#`, same-name replacement, external rename, stale protected-state revisions, and
policy denial. Resolver tests must assert that logs, status, metrics, and Events do not
contain external IDs or Secret values.
