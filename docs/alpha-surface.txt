SENTRY CONFIGURATION OPERATOR — ALPHA FIELD BOUNDARY
Date: 2026-10-31
Status: Accepted source/contract decision for the v1alpha1 schema

1. Publication rule

A field may enter the public CRD only when it has stable meaning independent of Sentry's
private database identifiers and can be validated or translated by a bounded adapter.
Source inspection for one version is not enough to claim cross-version or SaaS support.

2. Settings

Published settings are limited to typed inbound filters, bounded PII controls, advanced Relay
rules over built-in detectors and exact typed selectors, and the portable grouping-rule subset
whose public API shape is confirmed on the supported self-hosted versions. Raw Relay JSON,
regular expressions, grouping rule text, settings dictionaries, grouping profiles, and
secondary-grouping migration are not published.
The inbound-filter shape includes four boolean filters and an explicit set of the eight
non-deprecated legacy-browser families. An omitted field remains unmanaged; an explicitly
empty legacy-browser set disables every managed browser-family subfilter.
The behavior component contains only cross-version settings with bounded semantics:
auto-resolve hours, default environment, native crash-report retention, the
JavaScript/source-map scraping toggle, and a non-empty set of allowed DNS hostnames or HTTP(S)
origins. A leading wildcard subdomain and fixed port are supported, while `*` must be the sole
entry. Automatic release creation remains outside the common alpha surface; outbound TLS
verification remains platform policy.
Grouping enhancements contain one typed frame matcher and one action per ordered rule.
Fingerprinting rules contain one typed event matcher plus bounded literal fingerprint values and
an explicit include-default flag. The adapter owns and canonically serializes each complete list.
Sentry 26.10.1 rejects manual grouping-profile and secondary-grouping updates, so those fields
cannot enter the common contract even though 24.7.1 accepts them.
The symbolication settings component contains only the twelve built-in source identifiers
shared by both supported versions. It has complete-set semantics and a deterministic
serializer. The 26.10.1-only `proton` source and native source-server mapping are excluded
from the common contract.

Managed projects may also own bounded custom HTTP, S3, and GCS symbol-source children by
local DNS-label names. Credentials come only from keys in Secrets in the SentryProject
namespace. The controller generates deterministic external identities and ownership-bearing
remote names, pins only the identity, safe metadata, and a desired-state digest in protected
state, repairs visible drift, rotates credentials through a full update, and deletes only the
exact pinned source. Public status contains only local lifecycle state and source type. Azure
is excluded because it is not portable to 24.7.1.

3. Common alerts

The common alert surface contains:

- `first-seen` and `regression` for the legacy compatibility profile;
- `event-count` and `user-count`, `windowMinutes`, `threshold`, local destination
  references, and bounded enabled state where the selected adapter supports it.

The compatibility profile is explicit. The controller never chooses a legacy or modern
adapter from a version string alone.

4. Advanced features

Advanced Sentry condition trees, action payloads, detector families, workflow graphs, and
raw vendor JSON remain outside v1alpha1. They require a later typed contract or a separate
extension mechanism with its own ownership and compatibility guarantees.

5. Evidence

Generated CRDs and webhooks enforce the published shape. Envtest and kind prove Kubernetes
admission. Fixtures and adapter tests prove source contracts. Live Sentry configuration
acceptance is recorded separately and must not be conflated with event ingestion or
notification delivery.

6. Regional ownership and notification target evolution

The evolving alpha connection contract exposes a stable region name, Active or Standby
role, and positive monotonically increasing revision. The public term is revision, never
epoch. Existing unmarked projects default to Reject; Adopt is valid only on an Active
connection.

Slack workspaces and PagerDuty accounts are declared as stable local catalog aliases for
integrations already installed in Sentry. Declaration never installs an integration. Access
grants cover aliases, not channel or service allowlists. Projects and reusable policies use
provider-first maps under `notificationTargets`; alerts reference readable terminal names
such as `slack/backend-alerts` and `pagerDuty/Backend Primary`. Terminal names must be
unique within a provider. There is no legacy destinations spelling or compatibility shim.

7. Reusable alert policy

`SentryAlertPolicy` is cluster-scoped and self-service. Ordinary cluster RBAC determines
who may create, update, or delete policies; the API does not publish an owner field or a
custom authorization webhook. Any project may opt in with `spec.alertPolicy`. Policy and
project alert/target keys must not conflict, and each alert may reference only targets from
its own ownership scope. Protected child state records the exact project or policy UID so a
same-name recreation cannot inherit external Sentry objects.

8. Project team access

Managed projects may declare additional readable team slugs in `spec.grantAccess.teams`.
Every slug must be allowed by the namespace's connection access rule. The create team is
already attached and cannot be repeated. The controller pins each managed Sentry team
identity, grants or revokes through the public project-team endpoints, and never removes an
unmanaged team. Direct user access is not published because Sentry project access is
team-based.

9. Issue ownership

Managed projects may own the complete custom issue-ownership rule set through structured
`path`, `module`, `url`, and event-tag matchers. Rules reference only the primary project
team or readable team slugs declared in `grantAccess`; every referenced team remains subject
to the connection access rule. The public contract also exposes explicit unmatched-issue
fallthrough, auto-assignment mode, and synchronization of already imported CODEOWNERS data.
It does not expose raw ownership grammar, comments, quoted identifiers, direct users,
emails, or repository identities.

10. Repository code mappings and CODEOWNERS import

A connection may assign stable DNS-label aliases to already-installed source-code
integrations and their already-imported repositories. Managed projects select only those
aliases and may own bounded repository path mappings plus an optional CODEOWNERS import.
The operator resolves every catalog name exactly once, journals non-idempotent creates,
repairs visible mapping or CODEOWNERS drift, and deletes only protected exact identities.
Numeric integration, repository, mapping, and CODEOWNERS identities stay in protected state;
public status contains only local aliases and safe lifecycle state. Source-contract, unit,
admission, envtest, direct API, and full-controller live acceptance passes on both supported
Sentry versions. Provider-backed CODEOWNERS fetch remains an external integration boundary.

11. Managed client keys

Managed projects may own bounded client-key children by local DNS-label names. Each entry
controls active state, a portable count/window rate limit, and a positive monotonic rotation
revision. Sentry generates all key material. The public API exposes no key identity, public
key, secret key, or DSN; status contains only local lifecycle state, reason, and revision.
`dsn.managedClientKey` selects an active local entry and publishes only its public DSN to the
owned output Secret. Exact identities and ownership-bearing remote labels remain in
protected state. An absent map is unmanaged, while an explicit empty map removes only keys
proven to be owned by the exact project incarnation.
