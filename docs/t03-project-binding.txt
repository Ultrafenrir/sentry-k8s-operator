1. Protected state

internal/binding хранит version=v1 records как Opaque Secrets в отдельном
sentry-kubernetes-operator-state namespace:

- project binding именуется hash Kubernetes UID и привязывает точный namespace/name/UID;
- manager claim именуется hash canonical installation + organization + project slug;
- operation journal реализует T02 Load/CompareAndSwap и переживает новый Store instance;
- external project/child identities существуют только в protected state;
- Kubernetes resourceVersion используется для Update/Delete CAS;
- неизвестная/повреждённая версия fail closed как invalid protected record.

config/state устанавливается до controller layer. Обычный make undeploy удаляет state
RBAC, но намеренно сохраняет state namespace и binding Secrets для ownership recovery;
их удаление требует отдельного явно destructive шага и backup.

CanonicalInstallation сводит HTTPS host case, :443 и cosmetic root path. Разные
discovered aliases одной installation должны передать один discovered canonical URL;
разные host names без такого evidence намеренно не считаются одинаковыми.

2. Manager claim и handoff

AcquireClaim делает Kubernetes Create до внешней mutation. Повтор того же UID идемпотентен;
другой UID получает OwnershipConflict. Реальный envtest запускает две конкурентные Create
и доказывает один winner + один conflict.

Handoff одним claim CAS:

- проверяет source manager UID;
- сразу заменяет manager на exact target namespace/name/UID/generation;
- создаёт one-time authorization, дополнительно связанную с claim slug;
- target связывает уже существующий Managed project без POST только при marker + source
  protected binding + pinned external identity;
- authorization очищается после target binding; source немедленно теряет mutation право.

Store предоставляет низкоуровневую CAS primitive. Authenticated admin command, SubjectAccessReview
и полный recovery UX ещё не подключены; вызывать primitive из обычного reconcile нельзя.

3. Managed create state machine

Порядок:

1) policy Evaluate, canonical installation, deterministic slug;
2) GET preflight до claim для обычного existing slug;
3) Kubernetes manager claim; competing writer останавливается до POST;
4) protected binding с Planned intent, trusted owner, exact expected marker и desired hash;
5) повторный GET после claim;
6) повторное чтение claim непосредственно перед mutation;
7) binding phase Submitted;
8) identity-free closed-schema audit start; недоступный sink блокирует POST;
9) один non-RetrySafe POST с default_rules=false и atomic reserved name marker;
10) verify exact slug/marker, audit verified/recovered outcome, затем pin external identity и
    очистить pending.

Если POST response потерян, следующий reconcile делает только GET. Exact expected marker +
Submitted intent + matching claim восстанавливают identity. Если объект не найден или
evidence неполно, результат CreationOutcomeUnknown; POST вслепую не повторяется.
Если audit sink недоступен после успешного POST, Submitted intent сохраняется, а следующий
GET восстанавливает marker/identity и записывает Recovered без второго POST. Событие содержит
только local namespace/name, generation и fixed enums — не external identity, desired hash,
request/response или raw error.

Existing slug без handoff возвращает ProjectAlreadyExists до claim и никогда не adoption.
После bind новый object с тем же slug, другой identity или потерянный marker дают
OwnershipLost. Ручное удаление даёт ExternalDeleted и не вызывает auto-create.

4. Marker transport

Source-confirmed fallback реализован product-кодом:

  <displayName> [managed;o=<owner>;m=<managed-by>]

Parser принимает только полный exact suffix, lowercase alias grammar и максимум 50 Unicode
characters. Lookalike, delimiter injection, nesting и overflow отклоняются до POST.
HTTP adapter использует public routes:

- GET /api/0/projects/{organization}/{slug}/
- POST /api/0/teams/{organization}/{team}/projects/
- DELETE /api/0/projects/{organization}/{slug}/

Create body соответствует version-pinned 24.7.1/26.10.1 fixtures; platform omitted остаётся
omitted, default_rules=false сериализуется обязательно. POST/DELETE не transport-retryable.

5. ReadOnly classification

project.use после observe policy:

- никогда не создаёт manager claim и не выполняет mutation;
- новый remote marker без protected Manage binding остаётся External;
- matching marker + protected Manage binding классифицируется Managed, но reader binding
  получает AccessMode=ReadOnly без manager UID/claim;
- pinned identity не переключается после replacement;
- External не получает owner; Managed reader может показывать безопасное owner evidence,
  но owner ему не назначается как право.

6. Finalizer и deletion

Controller первым reconcile добавляет sentryconfiguration.io/project-protection и только
следующим reconcile допускает engine mutation. Retain удаляет finalizer без Sentry calls и
сохраняет orphan protected record. DeleteProject требует одновременно:

- create mode и текущую policy Manage;
- exact binding identity и marker;
- current manager claim без pending handoff;
- повторную authorization непосредственно перед DELETE;
- GET после DELETE, подтверждающий NotFound.

DELETE также записывает start до внешнего вызова и verified/recovered outcome до удаления
protected records. Audit failure до DELETE даёт zero-call; failure после подтверждённого
NotFound восстанавливается без второго DELETE.

Replacement с прежним slug не удаляется. project.use не удаляет внешний project. После
подтверждённого удаления claim и binding удаляются CAS, затем controller снимает finalizer.

CRD не предоставляет вызываемый HTTP subresource `/finalizers`: правило
`sentryprojects/finalizers:update` само по себе возвращает `yes` в SubjectAccessReview, но
controller-runtime subresource update получает 404, а обычный update авторизуется как
основной ресурс. Поэтому finalizer меняется точечным MergePatch от непосредственного
DeepCopy, а manager ClusterRole имеет только `patch` на SentryProject; `create`, `delete` и
`update` остаются запрещены. Persistent kind v1.35.5 подтвердил этот реальный service-account
path: finalizer появился до дальнейшей recovery, обе replica остались Ready без restart.

7. Capability honesty

Runtime Managed create требует в SentryConnection.status.capabilities одновременно:

- project.create.atomic-default-rules;
- project.create.automatic-active-key.

Без обеих controller выставляет ManagedCreateUnsupported до API call. Текущий
SentryConnection controller не повышает их на основе одной версии/source fixtures, поэтому
при недоступном Sentry реальный Managed create сознательно заблокирован. Injected envtest
evidence проверяет остальной vertical slice, но не считается Verified.
