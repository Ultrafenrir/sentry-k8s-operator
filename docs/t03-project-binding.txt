T03 — PROJECT, BINDING, AND OWNERSHIP
Updated: 2026-10-31
Status: Complete for source/mock/Kubernetes scope with disposable live recovery evidence

Protected state

Project bindings and operation journals live in the protected state namespace, outside
application namespaces. They store external identity, ownership markers, manager claim,
desired hash, operation phase, and compare-and-swap metadata. Public CR status exposes none
of those private values.

Managed creation

The state machine authorizes the namespace/team, records intent before the Sentry POST,
sends at most one create request, recovers a lost response by slug plus exact marker, verifies
the resulting project and active key, then commits the binding. A second blind POST is
forbidden.

The managed Sentry slug is always the Kubernetes `metadata.name`. The Sentry display name
is derived internally from that name, shortened only when necessary to preserve the complete
ownership marker within Sentry's limit. Neither slug nor display name is configurable in the
public create block.

Existing projects

Observation without DSN use does not take mutation ownership. Authorized DSN consumption
creates a local binding only for the required key identity. Same-name replacements and
external renames fail closed.

Additional team access

`spec.grantAccess.teams` manages additional exact team slugs on a managed project. The
connection access rule must authorize every requested team. Protected bindings pin the
external team identities, so a same-slug replacement fails closed and a removed desired
entry revokes only the previously managed identity. Teams attached outside this field are
preserved. Direct user membership remains outside the alpha contract.

Lifecycle

The finalizer handles protected cleanup before removing Kubernetes ownership. `Retain`
removes operator-owned child resources, verifies the exact project identity and manager
claim, removes the remote ownership marker, verifies the release by readback, and then
deletes the protected claim and binding while leaving the Sentry project in place.
For a managed Standby candidate, `Retain` first removes only that candidate's separately
owned alerts and destinations, then releases its read-only binding without changing the
manager claim or the remote project ownership marker.
`DeleteProject` requires current policy authorization, the exact manager claim, and live
ownership evidence. Deletion is processed even when the resource is paused.

Capability honesty

Managed creation requires both:

- `project.create.atomic-default-rules`;
- `project.create.automatic-active-key`.

The controller does not derive them from a version string. The local runbook applies them
only after live configuration acceptance against the disposable target.

Verification

`make verify-t03` covers journaling, lost-response recovery, claims, handoff, read-only
classification, team-access identity pinning, deletion, redaction, and failure injection.
Disposable live acceptance has also recovered an intentionally discarded project-create
response without a second POST. On 2026-10-31 clean disposable-stack runs also verified
additional-team grant, read-back, revoke, and primary-team preservation against Sentry
24.7.1 feature-complete and Sentry 26.10.1 errors-only.
