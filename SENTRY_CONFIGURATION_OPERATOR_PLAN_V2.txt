SENTRY KUBERNETES OPERATOR — PRODUCT PLAN V2
Revised: 2026-10-31
Status: Alpha implementation in progress

This plan defines product intent and sequencing. `docs/project-status.md` is the current
implementation and backlog summary. Git history retains the original long-form planning
record.

1. Product goal

Let a service owner declare Sentry configuration next to a Kubernetes workload using
readable names, while a platform administrator controls credentials, organizations, teams,
installed notification integrations, transport policy, and mutation permissions. Service
owners choose channels and services within the integrations exposed by the connection.

The operator must hide and protect Sentry IDs, API tokens, DSNs, integration keys, Telegram
numeric targets, operation journals, and delivery payloads. Status, Events, metrics, and logs
must remain useful without exposing that data.

The product is not a Sentry installer, a generic passthrough to every Sentry API, a secret
manager, or proof that an external notification provider delivered a message.

2. Public resources

`SentryConnection` is cluster-scoped and platform-owned. It selects one Sentry base URL and
organization, references credentials in the fixed operator namespace, chooses transport and
alert compatibility policy, and declares stable local names for existing Slack workspaces
and PagerDuty accounts. Declaring an integration never installs or creates it in Sentry. It
also declares the platform-owned regional ownership role and revision used for explicit
cross-region failover.

`SentryAlertPolicy` is the reusable team alerting contract. It selects one connection,
defines common notification targets by workspace/channel or account/service, and defines
common alerts that may be applied to many projects. Projects may add non-conflicting local
targets and alerts. Merge, rollout, ownership, compatibility, and deletion semantics must be
specified before this resource is published.

`SentryProject` is namespaced and service-owned. It selects exactly one of managed creation
or existing-project use, optionally publishes a DSN Secret, declares typed settings,
selects an optional alert policy, adds project-local notification targets and alerts, and
declares pause state and Retain/DeleteProject lifecycle behavior. Namespace scope is the
self-service RBAC and Secret-publication boundary; it does not define Sentry identity.

Public specs contain readable names and local keys. External identities exist only in
protected state. Status contains fixed conditions, readable names, and bounded summaries.

3. Core semantics

Name resolution is exact and fail-closed: zero matches are not found, multiple matches are
ambiguous, and one match is pinned. A later same-name replacement is never selected
silently.

Managed mutation requires authorization, ownership evidence, an idempotent operation
journal, at most one external mutation per reconcile, read-after-write verification, and a
redacted status update. Interrupted create/delete operations must recover by exact marker or
remain visibly uncertain; blind retries are forbidden.

DSN publication uses a Kubernetes Secret owned by the `SentryProject`. Rotation and output
name changes preserve the old usable value until an explicit cutover can be verified.

Omitted components are unmanaged. An explicitly empty owned map requests cleanup only for
objects whose protected ownership marker matches the project.

4. Self-service ownership and regional failover

The managed Sentry slug is exactly the `SentryProject` `metadata.name`; the operator does
not generate a region, namespace, hash, or other suffix for the external project name.
Remote project identity is the connection, organization, and slug tuple. A protected local
claim serializes that identity across namespaced CRs in one cluster.

Exactly one `SentryProject` may manage project settings and lifecycle for that identity.
Other authorized CRs enter `Standby`: they may consume a DSN and may contribute separately
owned alerts, but they may not mutate project settings, delete the project, or modify alerts
owned by another CR or policy. Alert ownership is independent from exclusive project
ownership. Conflicting alert keys or ownership evidence fail closed.

A requested Active role is an acquisition request, not permission to steal. Promotion
requires an unclaimed project, an exact handoff from the current manager, a clean release,
or an infrastructure-authorized regional takeover. A persistent boolean must not provide
force-takeover authority. Exact handoff binds the target namespace, name, UID, generation,
and slug so stale objects cannot complete it.

Existing projects without a recognized ownership marker follow a platform policy on
`SentryConnection`: `Reject`, `Standby`, or `Adopt`, with `Reject` as the safe default. Only
the Active region may adopt. Adoption requires namespace/team authorization, an atomic
local claim, a remote marker write, read-after-write verification, and an audit record.
Absence of a marker is not treated as technical proof that no human manages the project;
`Adopt` is an explicit platform policy decision.

Every connection deployment has a stable, human-readable region name and declares:

    ownership:
      region: eu-west-1
      role: Active
      revision: 8

The remote ownership marker includes region, revision, owner, and operator installation
identity. Revision is a positive, monotonically increasing failover number controlled by
the platform team. A larger revision fences every smaller revision. The same revision with
different regions is a conflict and all mutation fails closed. A stale region never
rewrites a larger revision and cannot reclaim ownership without a new explicit revision.

A regional takeover changes the standby connection to Active with a revision greater than
the remote marker. The controller writes the new marker, waits a bounded fencing interval,
reads it again, and only then mutates project settings, alerts, or lifecycle. Every external
mutation and every journal retry revalidates the exact region and revision immediately
before writing. The former region becomes Fenced/Standby when it observes the larger
revision. Failback is another explicit revision increase. Failover is connection-wide by
default; per-project regional overrides are deferred until a demonstrated need exists.

Coordination has three layers: Kubernetes leader election for replicas of one deployment,
an atomic protected project claim for competing CRs in one cluster, and the Sentry ownership
marker plus revision for different regions. This deliberately avoids an external quorum.
Without a conditional-write primitive in Sentry, one already in-flight request cannot be
proven impossible during a network partition; pre-write revalidation, bounded mutation
timeouts, fencing delay, read-after-write verification, and auditable manual revision
changes define the accepted operational boundary. Stronger linearizable fencing would
require credential revocation or an external coordinator and is not part of this design.

The ownership marker must not change the project slug. Its final Sentry storage location and
supported-version behavior require source and live acceptance evidence; the current display
name marker must not be silently presented as arbitrary project metadata.

5. Settings and alerts

The alpha settings surface is typed inbound filters plus typed PII controls. Arbitrary raw
Sentry settings and grouping profiles are excluded until portable semantics are proven.

The common alert catalog is adapter-neutral. Legacy 24.7.1 maps first-seen, regression, and
event-count to legacy issue/metric rules. Modern 26.10.1 maps event-count to a metric
detector/workflow. Compatibility is selected explicitly, never inferred from a version
string. External actions are resolved by local destination keys and protected pins.

6. Notification targets and Telegram

`SentryConnection` exposes stable local workspace and account names for integrations already
installed by the platform team. A policy or project selects any readable Slack channel or
PagerDuty service inside one exposed integration; the connection does not maintain a
channel/service allowlist. Provider-specific `workspace`/`channel` and `account`/`service`
fields are used instead of a generic `integrationRef`.

The operator resolves and pins existing integration and target identities for alert actions.
It never creates a Slack/PagerDuty integration, Slack channel, or PagerDuty service. A missing
or ambiguous integration, channel, or service fails closed. PagerDuty catalog resolution is
implemented. Slack remains fail-closed without one proven public channel catalog across
supported versions.

Telegram registration is a separate, Kubernetes-authorized flow. One-time challenges store
only hashes, bind to exact project/destination/policy identity, expire, and are consumed with
compare-and-swap semantics. Public receivers have no Kubernetes token; an internal mTLS
writer performs final authorization and protected-state mutation.

Telegram delivery uses an isolated durable at-least-once queue. It supports deterministic
dedupe, bounded retry, lease recovery, dead letters, retention, token rotation, and
identity-free metrics. Exactly-once delivery is not promised.

7. Security and lifecycle

Controller credentials, registration state, hook sources, routes, delivery queue, and audit
records use separate namespaces and RBAC boundaries. Receivers and workers receive only the
minimum data and permissions required for their role.

Retain removes Kubernetes ownership without deleting the Sentry project. DeleteProject
requires live policy authorization and ownership proof. Pause prevents ordinary mutation
but does not bypass safe deletion or protected recovery work.

The manager runs with leader election, two replicas, probes, disruption budget, bounded
jitter, transition-only Events, bounded-label metrics, and immutable redacted audit records.

8. Compatibility baseline

- Go: repository-pinned 1.26 toolchain.
- Kubernetes: 1.35 and 1.36 envtest/kind matrix.
- Sentry: self-hosted 24.7.1 legacy profile and 26.10.1 modern profile.
- SaaS: intentionally deferred until credentials and least-privilege scope acceptance exist.

Source inspection, fixtures, mocks, envtest, kind, live configuration CRUD, ingestion, and
external delivery are distinct evidence levels and must be reported separately.

9. Work sequence

T00: freeze external API, toolchain, fixtures, and evidence rules.
T01: publish the bounded v1alpha1 CRDs and admission contract.
T02: secure client, connection registry, policy, and exact resolvers.
T03: project ownership, protected bindings, journals, handoff, adoption, standby, regional
     fencing, and deletion.
T04: client keys, DSN authorization, and output Secret lifecycle.
T05: typed filters and PII settings with drift repair.
T06: destinations, pinning, revoke behavior, and Telegram registration.
T07: legacy and modern alert adapters with protected ownership.
T08: authenticated hook ingress and durable Telegram delivery.
T09: HA, security, recovery, audit, metrics, backup, and upgrade behavior.
T10: Helm/Kustomize packaging and supply-chain policy.

10. Current priority

Follow `docs/project-status.md`. The immediate API work is the self-service Active/Standby
ownership contract, connection-wide regional fencing, reusable alert-policy contract, and
connection-owned integration catalog described above. The implementation must preserve the
exact external project slug and evolve generated CRDs, protected state, admission, status,
controllers, samples, recovery tests, and documentation together. Other non-external work
is reproducible local demo automation, safe local integration fixtures,
capability-evidence automation, redacted API inventory, and Docker Desktop diagnostics.
Hosted release, SaaS, real provider delivery, public ingress, and production Alertmanager
routing are deferred by the repository owner.

11. Acceptance rule

No task is complete merely because code exists. Completion requires generated artifacts,
focused tests, negative and recovery cases, explicit secret/redaction checks, and an honest
evidence classification. A configuration-only result is never delivery evidence.
